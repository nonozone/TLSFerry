# TLSFerry Remote DNS Challenge Protocol

This document defines the public contract between a TLSFerry certificate executor and a hosted DNS challenge control plane. It allows the executor to complete ACME DNS-01 without receiving the control plane's authoritative DNS credentials.

The protocol client is implemented by the `tlsferry-cloud` DNS provider. A production TLSFerry Cloud endpoint is not included in Community Edition and is not yet generally available.

## Trust boundary

The control plane assigns one delegated validation target to one managed hostname:

```dns
_acme-challenge.nos.nonopen.com. CNAME domain-123.auth.tlsferry-dcv.com.
```

For each issuance job, the control plane creates a short-lived bearer token. The token must authorize exactly one account, job, managed hostname, and delegated validation target. It must never grant general access to the validation DNS zone.

The executor receives only:

- the control-plane API URL;
- the short-lived job token;
- the certificate job and cloud deployment credentials required for that job.

The executor does not receive the Cloudflare or authoritative DNS API token.

## Present a challenge

```http
PUT /v1/acme-challenges/{challenge_id}
Authorization: Bearer {job_token}
Content-Type: application/json
X-TLSFerry-Protocol-Version: 1
```

```json
{
  "domain": "nos.nonopen.com",
  "fqdn": "_acme-challenge.nos.nonopen.com.",
  "effective_fqdn": "domain-123.auth.tlsferry-dcv.com.",
  "value": "base64url-acme-dns-value"
}
```

`challenge_id` is an opaque, deterministic identifier generated by the executor. Repeating the same `PUT` must be idempotent and must not create duplicate TXT records.

The control plane must reject the request unless all of the following are true:

1. The job token is active, unexpired, and authorized for the job.
2. `domain` exactly matches the managed hostname assigned to the job.
3. `fqdn` is the expected `_acme-challenge` name for that hostname.
4. `effective_fqdn` exactly matches the validation target previously assigned to that hostname.
5. The stored CNAME delegation still points from `fqdn` to `effective_fqdn`.
6. `value` has the expected ACME DNS-01 value format and acceptable size.
7. The job has not completed, failed permanently, or been revoked.

The control plane creates or replaces only the TXT record at `effective_fqdn`. A successful response is any `2xx` status; `204 No Content` is preferred.

## Clean up a challenge

```http
DELETE /v1/acme-challenges/{challenge_id}
Authorization: Bearer {job_token}
X-TLSFerry-Protocol-Version: 1
```

The operation must be idempotent. The preferred success response is `204 No Content`. The CE client also treats `404 Not Found` as successful cleanup because the record is already absent.

The control plane should remove only the TXT record stored for the authenticated job and challenge identifier. It must not accept an arbitrary DNS name in the cleanup request.

## Error responses

The control plane should return a short, non-sensitive plain-text or JSON error message:

| Status | Meaning |
| --- | --- |
| `400` | Invalid challenge request |
| `401` | Missing or invalid job token |
| `403` | Domain or validation target is outside the job scope |
| `404` | Challenge resource is absent |
| `409` | Delegation or job state does not allow the operation |
| `429` | Job-scoped rate limit exceeded |
| `5xx` | Temporary control-plane or DNS provider failure |

Tokens, cloud credentials, ACME key authorization, and certificate private keys must never appear in an error response or log entry.

## Executor configuration

The current CE adapter resolves two fields from an environment or keychain credential profile:

```bash
export TLSFERRY_CLOUD_API_URL=https://app.tlsferry.com/api
export TLSFERRY_CLOUD_API_TOKEN=short-lived-job-token
```

```json
{
  "issuer": {
    "type": "acme",
    "email": "ops@example.com",
    "directory_url": "https://acme-v02.api.letsencrypt.org/directory",
    "challenge": "dns-01",
    "dns_provider": "tlsferry-cloud",
    "credential": "env:TLSFERRY_CLOUD"
  }
}
```

Production executors should inject the job token into an in-memory credential resolver or an isolated process environment for one job. They should not write it to a long-lived configuration file.

Plain HTTP is rejected except for loopback addresses used by local tests and development.
